crdblab
Project Hydra

A measurement harness for multi-cloud database failover

crdblab compares CockroachDB with PostgreSQL under Patroni on the same five-node, three-cloud testbed. It measures steady-state throughput and latency, then injects faults and measures how long the database stops serving writes (RTO) and whether any acknowledged write is lost (RPO).

What it does

One command provisions the testbed with Terraform, runs every measurement phase against CockroachDB, tears the testbed down, redeploys it as PostgreSQL/Patroni, runs the same phases again, and draws a 31-chart comparison. Every result is a self-describing run directory under runs/, so all analysis and figures can be regenerated later without a testbed.

Phase INetwork substrate: all-pairs RTT and the quorum floor
→
Phase IIBenchmark: throughput and latency across concurrency tiers
→
Phase IIIrecover fault: a 45 s network partition of the primary
→
Phase IVdead fault: the database process is killed

How the code fits together

Each layer only calls the ones below it. Select a module to open its code reference.

Design rules the code enforces

Most failures in this kind of study produce plausible, even flattering, numbers. The harness is built so that those failures stop a run instead.

Header-bound parsing

Generator output is bound to column names from its own header line. A data line before a header is an error, never a guess.

Operation type is a dimension

Throughput sums across reads and updates. Latency is always reported per operation, never pooled.

Runs are immutable and self-describing

Every run keeps a manifest (git revision, profile, topology, server flags, hardware) and the generator's raw output.

Two gates before analysis

Validation asks whether the numbers agree with each other. Pre-flight asks whether the system was fit to measure. load_run refuses a run that fails either.

A comparison is checked too

Two valid runs are only compared if their workload, server flags, cache budget, hardware and version match.

Concurrency is not load

Engines are compared along their throughput-latency curves, at matched throughput or utilisation, never at equal worker counts.

Silent instruments are not healthy ones

RTO clients record how much of the run they actually watched. An outage they did not see is reported as unmeasured, not absent.

Physical floors are asserted

A committed write cannot beat the round trip to the follower that completes quorum. Faster writes mean the workload touched no rows.

The testbed

Six virtual machines on three clouds, joined by a Tailscale mesh. Five form the database cluster; the sixth runs the load generator and is never part of the system under test. Only one engine is deployed at a time.

All six are 4 vCPU / ~8 GiB (c2d-highcpu-4, g6-dedicated-4, Standard_B4als_v2), as the latest run manifests record. GCP and Azure disks are 50 GB SSD. The topology is declared once in crdblab/topology.py; the shell scripts read it from there.

The fast triangle.

gcp-1, linode-1 and linode-2 are within ~70 ms of each other. A 3-of-5 quorum from gcp-1 needs two follower acknowledgements, so the second-fastest follower (linode-2) sets the write floor. Losing a triangle member pushes that floor to an Azure node, roughly 3x higher.

Guide

Measurement phases

Run in order: each phase uses what the previous one produced. Every phase writes one run directory named <UTC stamp>_<suffix>.

Phase I: network substrate

.venv/bin/crdblab net probe --profile thesis-extended
.venv/bin/crdblab --engine postgresql net probe --profile thesis-extended

From every node in parallel, pings every other node 100 times at 0.1 s intervals and records the RTT matrix, loss and Tailscale MTU into network.csv. It derives the quorum floor from the gateway's row, and asserts NTP clock offset on every node and (on CockroachDB) leaseholder placement. Run it once per deployment: switching engines replaces every cluster node.

Suffix _p1-network. Code: phases/p1_network.py.

Phase II: benchmark

.venv/bin/crdblab bench --profile thesis-extended
.venv/bin/crdblab --engine postgresql bench --profile thesis-extended

Sweeps the profile's concurrency tiers (thesis-extended: C = 1, 2, 5, 10, 50, 100, 200, three repetitions each) in an order shuffled from the profile seed and recorded in the manifest. Each tier runs cockroach workload run ycsb from client-1 with an 80/20 read/update mix and uniform keys, drops the warm-up, and writes one row per interval and operation to metrics.csv.

  • Refuses to start without a Phase I run to supply the quorum floor.
  • Before starting: clock offset, and leaseholder placement (CockroachDB) or primary placement (PostgreSQL).
  • Around every tier: a row-match probe and the write-latency floor check, so a workload touching no rows fails.
  • Records the server's start command, version and hardware, and polls node_exporter on all six machines.

Suffix _bench_cluster. Code: phases/bench.py.

Phases III and IV: fault injection

.venv/bin/crdblab chaos run --mode recover --profile thesis-extended   # Phase III
.venv/bin/crdblab chaos run --mode dead    --profile thesis-extended   # Phase IV
ModeCockroachDBPostgreSQL / Patroni
recovertailscale down, 45 s, tailscale up, detached so it survives the cut SSH session. The node heals itself.
deadkillall -9 cockroachInstalls a systemd drop-in with Restart=no, then kills the whole patroni.service cgroup.

A steady workload runs at the profile's chaos concurrency. A timer thread injects the fault inject_at_s seconds after the generator's first sample. The run is extended so at least min_post_fault_s of observation follows the fault (counted from the heal in recover mode). Three clients watch it:

Generator

Throughput per second. Gives performance RTO: the start of the first window where throughput holds above 80% of baseline for 10 s.

Audit writer

Serial writes, each ack, ambiguous or refused. Gives RPO and an availability RTO at ~70 ms resolution.

RTO probe

Eight concurrent canary writers on client-1. Gives availability RTO at ~20-30 ms resolution.

Before the fault: the fault must be permitted (a harmless command with the same privileges), the probe agent must be able to run, and placement must be correct. On PostgreSQL the primary is switched back to gcp-1 first, then resolved live; the fault hits whichever node actually answers /primary. After every artefact is written, a dead target is restarted and the restore is recorded separately in events.json.

Suffixes _p4-chaos-recover, _p4-chaos-dead. Code: phases/p4_chaos.py. The probe alone: crdblab probe rto --duration 60 (suffix _p4-probe).

After measuring

for m in runs/*/metrics.csv; do .venv/bin/crdblab validate "$(dirname "$m")"; done
.venv/bin/crdblab analyze steady-state <bench-run>
.venv/bin/crdblab analyze engine-comparison --crdb <run> --pg <run>
.venv/bin/crdblab analyze resilience <chaos-run>
.venv/bin/crdblab report figures              # newest run of each phase, PNG + SVG
./generate_insights.sh --profile thesis-extended

Add --json to analyze and validate for machine-readable output. Every figure and chart loads its runs through the gated loader, so an unvalidated run cannot reach one.

Guide

Measurement concepts

The quantities the harness reports, what limits each one, and the checks that stand between a run and a figure.

The quorum floor

A write commits when a majority of voters has it: the leader plus voters // 2 followers. So no write can be faster than the round trip to the slowest of the fastest voters // 2 followers. Patroni's ANY 2 synchronous standbys give the same geometry, so one floor bounds both engines. Try it with the testbed's RTTs from gcp-1:

–

Code: preflight.quorum_floor_ms. Each Phase II tier fails if its update p50 is below 90% of the floor.

Row match: is the workload touching data?

The generator derives keys from a seed. If the seed or row count differs from the values the table was loaded with, every lookup matches nothing and returns in ~3 ms, so the run reports roughly twenty times the throughput. It does not error. Two independent checks catch it in every tier:

  • Row-match rate must be at least 0.99. CockroachDB: crdb_internal.statement_statistics differenced across the tier. PostgreSQL: idx_tup_fetch / idx_scan from pg_stat_user_tables; any sequential scan fails the tier.
  • Write-latency floor: an update median below the quorum floor is impossible.

CockroachDB flushes its statistics every 10 minutes. A flush mid-tier falls back to the absolute counters; a flush after the tier ends is accepted only if the floor check independently passed.

Two clocks

The generator's elapsed_s starts when it begins issuing operations. The harness's monotonic clock starts earlier, by the SSH and process startup cost (about 5 s). Faults and all events.json offsets use the harness clock, so every metrics row records both (wall_offset_s, schema 2.1). For older schema 2.0 runs the offset is only bounded, and analyze resilience reports timings as intervals; figures draw the fault as a band instead of a line.

Three RTO readings and RPO

FigureSourceMeaning and limit
Availability RTOaudit.csvFault to writes resuming: the largest post-fault gap between acknowledged writes above the healthy noise floor. Resolution is one quorum write (~70 ms).
Probe RTOrto_probe.csvThe same quantity at ~20-30 ms resolution. Prefer observed_outage_s (probe-to-probe, link delay cancels). A gap is only attributed to the fault if gaps above the healthy p95 became more frequent afterwards.
Performance RTOmetrics.csvThroughput back above 80% of baseline and held for 10 s. Reported as undefined if the cluster settles into a lower stable state, which happens when a fast-triangle member is lost.
RPOaudit.csv + tableAcknowledged writes missing from the table afterwards. Ambiguous writes are counted separately; refused writes were never promised.
Check coverage first.

A client blocked on a black-holed connection stops observing and produces no gap, which reads as "no outage". Both RTO clients record how much of the run they watched; when coverage_truncated is true, the outage is reported as unmeasured and analyze resilience prints *** AN INSTRUMENT STOPPED OBSERVING ***. Connections use TCP keepalives and tcp_user_timeout so a partition breaks them instead of hanging them.

Comparing the engines

Concurrency fixes the number of workers, not the load. Two engines at the same tier sit at different points on their curves, so analyze engine-comparison reports:

  • Throughput-latency curves for both engines, per operation.
  • Matched throughput: latency ratio at measured throughputs both engines reached, with each side's utilisation. Quote the least confounded point.
  • Matched utilisation: both engines at the same fraction of their own peak (different throughputs).
  • Lightest-load write median: at C = 1 one operation is in flight, so neither median contains queueing.
  • Same-concurrency delta: computed, but printed under NOT A RESULT.

It refuses to compare runs whose workload parameters, cache budget (--cache vs shared_buffers), CPU model, CPU count or memory differ. --accept-hardware-difference downgrades a hardware mismatch to a recorded warning.

Pre-flight and validation checks

Pre-flight before measuring

  • clock_offset: NTP offset below 250 ms
  • leaseholder_placement: all ycsb leases in the gateway region
  • patroni_primary_placement: primary on gcp-1, repaired by switchover
  • quorum_floor_available: a Phase I run exists
  • row_match, write_latency_floor: per tier
  • fault_authorisation, probe_agent_ready: chaos only

Validation after measuring

  • plausibility: no sample above tps_ceiling
  • quantile_ordering: p50 ≤ p95 ≤ p99 ≤ pMax
  • littles_law: N / X not below the weighted median
  • sample_cadence (warning), op_coverage, error_monotonicity
  • Probe log: ordering, known outcomes, no repeated sequence numbers
  • Cross-run: run_comparability

Troubleshooting

Problems that recur across redeployments, and how to fix them.

A tier fails row_match

The loaded table's seed or row count does not match the profile. Reload without --skip-load. When moving from smoke (125k rows) to a thesis profile, the table must be reloaded; run-experiment.sh refuses to start if it has fewer rows than the profile needs.

Lease preferences are not headed by the gateway region

run-experiment.sh stops here. Re-order on the live cluster; leases move within seconds.

ssh ubuntu@crdb-gcp-1 "cockroach sql --insecure --host=\$(tailscale ip -4):26257 -e \
  \"ALTER RANGE default CONFIGURE ZONE USING lease_preferences =
    '[[+region=us-east1], [+region=us-east], [+region=us-west]]';\""

A CockroachDB node is still down after a dead run

The chaos phase and run-experiment.sh both try to restart it. CockroachDB has no systemd unit, so restart it by hand with the same memory flags as its peers and a different live node to join:

ssh ubuntu@crdb-gcp-1 'TS_IP=$(tailscale ip -4); sudo -n cockroach start --insecure \
  --store=/var/lib/cockroach --listen-addr=$TS_IP:26257 --advertise-addr=$TS_IP:26257 \
  --locality=cloud=gcp,region=us-east1 --cache=0.25 --max-sql-memory=0.25 \
  --join=crdb-linode-1:26257 --background </dev/null >/dev/null 2>&1'

A Patroni member will not rejoin

After a partition the old primary must be rewound or re-cloned; the template keeps 4 GB of WAL and falls back to a fresh basebackup. Only Quorum Standby / streaming on the leader's timeline can take leadership back; read the Role and TL columns of patronictl list. To force a re-clone and switch back:

ssh ubuntu@crdb-gcp-1 'sudo -n systemctl stop patroni && sudo -n rm -rf /var/lib/postgresql/16/data && sudo -n systemctl start patroni'
sudo -n patronictl -c /etc/patroni/config.yml list
sudo -n patronictl -c /etc/patroni/config.yml switchover --leader <leader-hostname> --candidate crdb-gcp-1 --force

patronictl names members by hostname (crdb-gcp-1), not the short node name. Settings under bootstrap.dcs apply only at first bootstrap; change a live cluster with patronictl edit-config.

"The statement-statistics view was flushed after this tier ended"

CockroachDB flushes statement statistics every 10 minutes. The tier still passes if the write-latency floor check covers it. Do not raise sql.stats.flush.interval: suppressing the flush would change the throughput being measured.

"Access to crdb_internal and system is restricted"

Prefix manual queries with SET allow_unsafe_internals = true;, as the harness does for its statistics query only.

A fresh deployment is not ready

run-experiment.sh waits up to 600 s for all five nodes (CockroachDB) or all five /health 200s (PostgreSQL; 503 means still taking a basebackup). If a node never comes up, read /var/log/cloud-init-output.log on it. A Patroni node with no process usually means the config is not at /etc/patroni/config.yml.

engine-comparison refuses

Read the refusal: it names what differs (workload keys, cache budget, CPU, memory, version). Run both engines with the same profile on the same machine types. Absolute throughput varies between deployments; compare ratios and recovery behaviour.

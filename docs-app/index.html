Project Hydra · crdblab

Measure how databases fail and recover across three clouds.

crdblab runs the same experiment on CockroachDB and PostgreSQL/Patroni across GCP, Linode and Azure: it measures throughput and latency, then breaks the primary on purpose and records how long writes stop (RTO) and whether any are lost (RPO).

Set up from scratch → Run an experiment

Four phases, one run

Each engine goes through the same four phases, in order. Every phase writes its own run directory under runs/.

Phase I
NetworkRound-trip times between every pair of nodes, and the slowest a write can possibly be.
Phase II
BenchmarkThroughput and latency as the number of concurrent clients rises.
Phase III
PartitionThe primary is cut off the network for 45 s, then comes back.
Phase IV
CrashThe primary's database process is killed and stays down.

What one command does

./run-experiment.sh runs the whole study unattended. It does the following for CockroachDB, then again for PostgreSQL:

01ProvisionTerraform creates 6 VMs on 3 clouds.
02WaitCloud-init installs the database.
03MeasurePhases I–IV, then validation.
04Tear downVMs destroyed; billing stops.
05Compare31 charts and the engine comparison.

3Create an SSH key

Terraform installs your public key on every VM, and the harness logs in with it. The harness runs ssh without choosing a key, so the key must be one ssh uses by default. Use RSA: Azure VMs require it.

ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_rsa     # skip if ~/.ssh/id_rsa already exists
cat ~/.ssh/id_rsa.pub                            # you'll paste this in step 6

If the key has a passphrase, load it into the agent first (ssh-add ~/.ssh/id_rsa), because the harness can't answer prompts.

4Set up Tailscale

Tailscale is a private network joining your machine and all six VMs. The harness reaches every VM by name (crdb-gcp-1, …) over it, and no database port is open to the internet.

  1. Create a free account at login.tailscale.com and sign in on this machine (sudo tailscale up on Linux, or the app on macOS).
  2. In the admin console, open DNS and make sure MagicDNS is enabled.
  3. Open Settings → Keys and generate an auth key with Reusable turned on (all six VMs use the same key). Keep it for step 6.
  4. On the same page, generate an API access token. Put it in .env: 
    TS_API_KEY="tskey-api-…"
    The pipeline uses it to remove the VMs from your tailnet after each teardown.

Both keys expire (at most 90 days). If a deploy fails at tailscale up or the cleanup step reports 401, create new ones.

6Configure HCP Terraform

Terraform runs remotely in HCP Terraform, which stores the state and all credentials. Nothing secret is kept in the repository.

  1. Sign up at app.terraform.io and create an organization.
  2. Create a workspace named hydra using the CLI-driven workflow.
  3. Point the repository at your organization. In terraform/providers.tf, replace lightygi with your organization name: 
    cloud {
  organization = "your-org"
  workspaces { name = "hydra" }
}
  4. Log the CLI in: terraform login.
  5. In the workspace, open Variables and add these environment variables, all marked Sensitive:
    VariableValue from

    ARM_CLIENT_ID, ARM_CLIENT_SECRET, ARM_TENANT_ID, ARM_SUBSCRIPTION_IDThe Azure service principal
    LINODE_TOKENThe Linode personal access token
  6. Add these Terraform variables. Copy the values from terraform/terraform.tfvars.example, and tick HCL for the four *_config maps:
    VariableValue
    ssh_public_keyContents of ~/.ssh/id_rsa.pub
    tailscale_auth_keyThe reusable auth key (sensitive)

8Do a first run

Start with the smoke profile: about 14 minutes of measurement per engine plus provisioning time. It proves the whole chain works before you commit to a run that takes hours.

tmux new -s hydra                 # detach with Ctrl-b d, reattach with: tmux attach -t hydra
./run-experiment.sh               # choose "smoke" when asked

When it finishes you'll have run directories in runs/ and a chart dashboard at insights/<stamp>_smoke/dashboard.html. Then run the real study with thesis-extended. Running experiments explains each step and what to do if one fails.

Running experiments

run-experiment.sh has two modes. With no arguments it runs the full pipeline for both engines. With arguments it measures only the engine currently deployed.

Full pipeline

./run-experiment.sh                                                  # interactive
.venv/bin/python pipeline/run_all.py --profile thesis-extended --yes   # no prompts

Select a step to jump to its details.

Steps 2–6 run once for CockroachDB, then again for PostgreSQL/Patroni.

  1. Pre-flight. Checks the harness is installed, terraform, tailscale and ssh are on your PATH, Tailscale is up and TS_API_KEY works. Removes stale testbed devices from the tailnet.
  2. Plan and apply. terraform plan -var=database_engine=<engine>, then terraform apply. Any error stops the pipeline.
  3. Wait for the VMs. Waits for SSH and for cloud-init to finish on all six machines.
  4. Measure. Runs ./run-experiment.sh --engine <engine> --profile <profile>: load data, phases I–IV, validation and analysis. See One engine.
  5. Log out. Logs Tailscale out on every VM.
  6. Destroy. terraform destroy, then deletes the VMs' tailnet devices so the next deploy gets the same hostnames.
  7. Insights and comparison. ./generate_insights.sh and crdblab analyze engine-comparison on the two newest bench runs.

If a step fails or you press Ctrl-C while VMs may be up, the pipeline asks whether to destroy them or leave them for debugging (--on-failure ask|destroy|leave). To rerun only the second engine, pass --engines postgresql.

Logs: runs/_logs/pipeline-<stamp>.log. Preview the UI without any cloud calls: pipeline/run_all.py --dry-run.

One engine

Any argument switches to measuring the engine already on the testbed. It stops at the first failed check.

OptionEffect
--profile <name>Profile to run (thesis-extended ≈ 75 min).
--smokeShort self-test with the smoke profile (≈ 14 min).
--engine postgresqlThe deployed engine is PostgreSQL. Default cockroachdb.
--skip-loadThe working set is already loaded.
--no-chaosRun phases I and II only.
--askChoose options interactively.

--engine doesn't deploy anything. It names the engine Terraform last stood up; the wrong engine fails the testbed checks.

  1. Check the workstation: the venv exists, Tailscale is up, and DB_URI is set (derived per engine, or from DB_URI_<ENGINE>).
  2. Check the testbed: waits up to 600 s for all five nodes. CockroachDB must have lease_preferences headed by the gateway's region; PostgreSQL must have exactly one primary.
  3. Load the working set with the profile's seed and insert_count, then check the row count. Skipped with --skip-load.
  4. Run phases I–IV. III and IV are skipped with --no-chaos.
  5. Restore the testbed: restarts the node killed in phase IV and, on PostgreSQL, switches the primary back to gcp-1.
  6. Validate every new run with crdblab validate.
  7. Analyse: steady-state and resilience reports, and figures in figures/.

Logs: runs/_logs/experiment-<stamp>.log.

Measurement phases

The phases run in order, and each uses what the previous one produced. Each writes one run directory named <UTC stamp>_<suffix>.

Phase I: network

.venv/bin/crdblab net probe --profile thesis-extended

Every node pings every other node 100 times at 0.1 s intervals. The RTT matrix, loss and MTU go into network.csv, and the quorum floor is derived from the gateway's row. It also checks NTP clock offset on every node, and leaseholder placement on CockroachDB. Run it once per deployment.

Run suffix _p1-network · crdblab/phases/p1_network.py

Phase II: benchmark

.venv/bin/crdblab bench --profile thesis-extended

Sweeps the profile's concurrency tiers (thesis-extended: 1, 2, 5, 10, 50, 100, 200, three repetitions each) in a shuffled order. Each tier runs a YCSB workload (80% reads, 20% updates, uniform keys) from client-1, drops the warm-up, and writes one row per interval and operation to metrics.csv.

  • Refuses to start without a Phase I run.
  • Checks clock offset and leaseholder (CockroachDB) or primary (PostgreSQL) placement before starting.
  • Checks row match and the write-latency floor around every tier.
  • Records the server's start command, version and hardware, and samples CPU, disk and network on all six machines.

Run suffix _bench_cluster · crdblab/phases/bench.py

Phases III and IV: fault injection

.venv/bin/crdblab chaos run --mode recover --profile thesis-extended   # Phase III
.venv/bin/crdblab chaos run --mode dead    --profile thesis-extended   # Phase IV
ModeCockroachDBPostgreSQL / Patroni
recovertailscale down for 45 s, then tailscale up. The node heals itself.
deadkillall -9 cockroachKills the whole patroni.service with automatic restart disabled.

A steady workload runs at the profile's chaos concurrency. The fault fires inject_at_s seconds in, and the run continues for at least min_post_fault_s afterwards. Three clients observe it:

ClientRecordsGives
Workload generatorThroughput per secondPerformance RTO
Audit writerSerial writes, each ack, ambiguous or refusedRPO, and availability RTO (~70 ms resolution)
RTO probeEight concurrent canary writers on client-1Availability RTO (~20–30 ms resolution)

On PostgreSQL the primary is switched back to gcp-1 before the fault, and the fault hits whichever node is actually primary. After a dead run the target is restarted, and the restore is recorded in events.json.

Run suffixes _p4-chaos-recover, _p4-chaos-dead · crdblab/phases/p4_chaos.py

Metrics and checks

What the harness reports, what limits each number, and the checks a run must pass before it reaches a chart.

RTO and RPO

MetricSourceMeaning
Availability RTOaudit.csvTime from the fault until writes resume: the largest post-fault gap between acknowledged writes. Resolution ~70 ms.
Probe RTOrto_probe.csvThe same quantity at ~20–30 ms resolution. Prefer observed_outage_s.
Performance RTOmetrics.csvTime until throughput is back above 80% of baseline and holds for 10 s. Undefined if the cluster settles lower.
RPOaudit.csvAcknowledged writes missing from the table afterwards. Ambiguous writes are counted separately.

Check coverage before trusting an RTO. A client stuck on a dead connection stops observing, which looks like "no outage". When coverage_truncated is true, the outage is reported as unmeasured and analyze resilience prints *** AN INSTRUMENT STOPPED OBSERVING ***.

The quorum floor

A write commits once a majority of the five voters has it: the leader plus two followers. So no write can be faster than the round trip from gcp-1 to its second-closest follower. Patroni's quorum mode (ANY 2 synchronous standbys) has the same geometry, so one floor bounds both engines.

Each Phase II tier fails if its update median is below 90% of the floor.

Row match

If the generator's seed or row count differs from what the table was loaded with, every lookup misses and returns in ~3 ms. The run reports about twenty times the real throughput, without any error. Two checks in every tier catch this:

  • Row-match rate must be at least 0.99 (from crdb_internal.statement_statistics on CockroachDB, pg_stat_user_tables on PostgreSQL).
  • Write-latency floor: an update median below the quorum floor is impossible.

Comparing engines

The same concurrency puts the two engines at different points on their throughput–latency curves, so comparing at equal worker counts is misleading. analyze engine-comparison reports instead:

  • Matched throughput: the latency ratio at throughputs both engines reached.
  • Matched utilisation: both engines at the same fraction of their own peak.
  • Lightest-load write median: at concurrency 1, where there is no queueing.

It refuses to compare runs whose workload, cache budget, CPU or memory differ. --accept-hardware-difference turns a hardware mismatch into a recorded warning.

Troubleshooting

Recurring problems and how to fix them.

A tier fails row_match

The loaded table doesn't match the profile's seed or insert_count. Rerun without --skip-load. Moving from smoke to a thesis profile always needs a reload.

Lease preferences not headed by the gateway region

Reorder them on the live cluster; leases move within seconds:

ssh ubuntu@crdb-gcp-1 "cockroach sql --insecure --host=\$(tailscale ip -4):26257 -e \
  \"ALTER RANGE default CONFIGURE ZONE USING lease_preferences =
    '[[+region=us-east1], [+region=us-east], [+region=us-west]]';\""

CockroachDB node still down after a dead run

CockroachDB has no systemd unit. Restart it by hand, joining a different live node:

ssh ubuntu@crdb-gcp-1 'TS_IP=$(tailscale ip -4); sudo -n cockroach start --insecure \
  --store=/var/lib/cockroach --listen-addr=$TS_IP:26257 --advertise-addr=$TS_IP:26257 \
  --locality=cloud=gcp,region=us-east1 --cache=0.25 --max-sql-memory=0.25 \
  --join=crdb-linode-1:26257 --background </dev/null >/dev/null 2>&1'

Patroni member won't rejoin

Check the Role and TL columns of patronictl list. To force a re-clone and switch the primary back:

ssh ubuntu@crdb-gcp-1 'sudo -n systemctl stop patroni && sudo -n rm -rf /var/lib/postgresql/16/data && sudo -n systemctl start patroni'
sudo -n patronictl -c /etc/patroni/config.yml list
sudo -n patronictl -c /etc/patroni/config.yml switchover --leader <leader-hostname> --candidate crdb-gcp-1 --force

patronictl uses hostnames (crdb-gcp-1), not short node names. Change a live cluster's settings with patronictl edit-config.

"The statement-statistics view was flushed after this tier ended"

CockroachDB flushes statistics every 10 minutes. The tier still passes if the write-latency floor check covers it. Don't raise sql.stats.flush.interval; that would change the throughput being measured.

"Access to crdb_internal and system is restricted"

Prefix manual queries with SET allow_unsafe_internals = true;.

A fresh deployment isn't ready

run-experiment.sh waits up to 600 s. If a node never comes up, read /var/log/cloud-init-output.log on it. On PostgreSQL, a /health 503 means the node is still taking a base backup.

Hostnames get a -1 suffix

Old devices are still in the tailnet after a manual terraform destroy. Remove them:

.venv/bin/python pipeline/run_all.py --tailscale-list
.venv/bin/python pipeline/run_all.py --cleanup --engine cockroachdb

engine-comparison refuses

The refusal names what differs (workload, cache budget, CPU, memory, version). Run both engines with the same profile on the same machine types.

test_insights.py fails

It renders charts from specific committed smoke runs and expects them to be the newest in runs/. Newer smoke runs make three of its tests fail.
